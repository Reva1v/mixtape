# Mixtape Constitution

## Core Principles

### I. Производительность прежде всего
Mixtape — личный музыкальный плеер, и скорость в нём важнее остального. Бюджеты обязательны,
регрессия любого из них блокирует слияние:
- холодный старт до интерактивного окна — не более 1.5 с;
- RAM в простое (окно открыто, музыка играет) — не более 150 МБ суммарно по всем процессам;
- переключение на локальный или предзагруженный трек — не более 150 мс до звука;
- поиск по локальной библиотеке на 20 000 треков — не более 50 мс;
- анимации и скролл — 60 fps без дропов, списки длиннее 100 элементов MUST быть виртуализированы.

Декодирование и вывод звука MUST выполняться в Rust-ядре, а не в WebView, чтобы
нагрузка UI не влияла на воспроизведение. Rust не шлёт в UI события чаще 10 Гц;
плавность (позиция, прогресс) интерполируется на стороне UI.

### II. Интерфейс как продукт
Красивый и удобный интерфейс — главная ценность наравне со скоростью. Фича считается
готовой только когда доведена визуально: состояния загрузки, пустые состояния, ошибки,
hover/active, переходы. Все основные действия MUST быть доступны с клавиатуры.
Второстепенные функции (тексты песен, диагностика, тонкие настройки) MUST быть спрятаны
за явной кнопкой и не занимать место в основном интерфейсе.

### III. Local-first
Источник правды — локальная библиотека: SQLite + аудиофайлы и обложки на диске.
Всё скачанное MUST воспроизводиться без сети. Сеть используется только для синхронизации
с YouTube Music, миксов (радио), поиска по каталогу и стрима ещё не скачанных треков.
Стрим MUST кэшироваться на диск с предзагрузкой следующих треков очереди.

### IV. YouTube за одной границей
Весь доступ к YouTube / YouTube Music MUST проходить через один модуль ядра `yt`
с собственными доменными типами; остальной код не знает о RustyPipe, InnerTube и yt-dlp.
Поломка со стороны YouTube MUST чиниться правкой только этого модуля. Cookies аккаунта
используются для чтения библиотеки и персональных миксов; массовая загрузка аудио
MUST идти с ограничением параллельности и паузами.

### V. Простота личного приложения
Один пользователь, одна платформа (Windows 10/11 x64). Нет своих серверов, аккаунтов,
телеметрии, автообновлений через сторонние сервисы и кроссплатформенных абстракций.
Новая зависимость или слой абстракции MUST иметь конкретную причину в спеке/плане (YAGNI).

### VI. Clean-room относительно Liner
Liner (`../desktop`) — только референс идей и раскладки интерфейса. Его код, шейдеры,
алгоритмы, ассеты и брендинг MUST NOT копироваться: лицензия Liner это запрещает.
Сторонние открытые библиотеки допустимы по их собственным лицензиям.

## Стек и ограничения

- Оболочка: Tauri 2. Ядро: Rust (stable), cargo workspace с крейтами по доменам
  (`yt`, `audio`, `library`, `sync`, `win` и т.п. — точный состав фиксирует план).
- Звук: symphonia (декодирование) + cpal/WASAPI (вывод); gapless обязателен.
- Данные: SQLite с FTS5 для поиска; файлы библиотеки в каталоге данных приложения.
- UI: Svelte 5 + TypeScript + Tailwind CSS 4 + Vite. Без React.
- Интеграция с Windows: SMTC и медиаклавиши, кнопки на миниатюре в панели задач.
- Тексты песен — опциональный модуль, выключен по умолчанию, открывается по кнопке.

## Процесс разработки

- Фичи ведутся по Spec Kit: specify → clarify → plan → tasks → analyze → implement,
  артефакты в `specs/<NNN-name>/`. Баги — через `/speckit-bug-*`; правки в один файл — без флоу.
- Ядро покрывается unit-тестами `cargo test` (очередь, библиотека, синхронизация, разбор
  ответов YouTube на сохранённых фикстурах). Тесты MUST NOT ходить в сеть.
- Перед коммитом проходят `cargo clippy -- -D warnings`, `cargo test`, `svelte-check`.
- Сообщения коммитов — на английском.

## Governance

Конституция имеет приоритет над остальными практиками проекта. План каждой фичи MUST
содержать проверку соответствия принципам I–VI; отклонение допускается только
с письменным обоснованием в плане. Изменения конституции — по semver: MAJOR при
удалении/переопределении принципа, MINOR при добавлении, PATCH при уточнениях.
